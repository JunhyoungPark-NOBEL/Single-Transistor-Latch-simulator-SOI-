# STL simulator 실행시간 벤치마크

2026-09-26. 같은 호스트에서 실제 계산 함수를 실행해 얻은 시간이다. 모델의 정확도를 비교하는 표가 아니다. Detailed와 Simple은 외부 입력과 수치 허용오차가 같아도 파형과 적응 시간 간격 수가 다르다.

## 측정 조건

- CPU: AMD EPYC 9V74 80-Core Processor를 사용하는 공유 실행 환경. 노출 논리 CPU 9개, 컨테이너 CPU quota 8개. 개별 계산의 BLAS/OMP/Numba 스레드 제한은 1개.
- Linux x86_64, Python 3.12.14, NumPy 2.3.5, SciPy 1.17.0, Numba 0.67.0.
- 표는 워밍업 이후 계산 함수의 벽시계 시간 중앙값이다. 보통 모델 순서를 번갈아 5회 측정했다. 일반 확률 모델의 기본 격자는 3회, 혼합 회로와 예측 확인용 회로는 2회다.
- HTTP, 대기열, 결과 직렬화, 네트워크, 브라우저 그래프 그리기, API 결과 캐시 적중 시간은 제외했다. 각 계산 함수 안의 준비와 결과 배열 구성은 포함한다.
- 회로는 Detailed/Simple 쌍을 시작하기 전에 프로파일 캐시를 한 번 비우고, 두 모델의 최초 계산 뒤 캐시를 유지하며 반복했다. 모든 회로가 요청된 종료 시각에 도달했는지 확인했다.
- Numba 디스크 캐시는 유지했다. first_call_s는 모듈 import 뒤 해당 작업의 첫 계산이며, Python 설치·완전히 비어 있는 JIT 캐시에서의 최초 구동 시간을 뜻하지 않는다.
- 확률 모델의 전이율/분기 표 캐시는 측정 배치별 새 폴더에서 시작했다. 반복 구간에서는 표를 재사용한다. 입력 파라미터가 바뀌면 표 생성 시간이 다시 생길 수 있다.

## 실행 전 시간 예측

브라우저 CPU 이름으로 시간을 단정하지 않는다. 로컬 버전은 로컬 Python 계산 프로세스를, 연구실 서버 버전은 연구실 서버의 계산 프로세스를 짧게 측정한다. 기준 표의 같은 모델·같은 계산 종류에 대한 비율로 보정하고, 이후 완료된 실제 작업의 관측값으로 갱신한다. 실패하거나 종료 시각에 못 도달한 회로는 학습에 쓰지 않는다.

아직 실행하지 않은 조건은 아래 작업량 근사와 가까운 표 항목을 사용한다. 결과는 예상 범위이며 보장 시간은 아니다.

- ID–VD: 상태 격자 수. 게이트 스윕: 격자 수 × 게이트 점 수.
- 확률 VSCM: 표를 재사용하는 고정 비용 + 반복 횟수 × VD 격자 수. 기준 자동 경로의 10/100회 측정은 약 0.01758 s + 0.001634 s × N에 대응했다. 일반 경로는 별도 측정값과 표 노드 수를 사용한다. 새로운 표의 생성 시간은 이 반복 계산 근사에 포함되지 않는다.
- 확률 게이트 스윕: 게이트 점 × 격자 × 표 노드 수. 이 경로는 해석적 혼합 분포를 사용하므로 n_cycles를 바꾸는 것이 실행 횟수 증가를 뜻하지 않는다.
- CSVM/회로: 최소 시간 간격 수 T/dt_max와 주입 전하 I·T/C_drain을 함께 반영한다. UI가 dt_max = T/3000으로 바꾸어도 더 긴 발진 구간에 더 큰 작업량을 배정한다. Body 커패시터를 drain 커패시터로 오인하지 않는다.
- 회로 소자 수, 반복 실행 수, 파형 주기 수, 허용오차도 작업량에 반영한다. 이 계수는 시간 예측용 휴리스틱이며 새로운 소자 물리나 발진 주파수 공식을 추가한 것이 아니다.
- 전하 평형은 상태 점 수, HRS 보정은 데이터 점 수/보정 변수 수를 반영한다. 혼합 회로와 기본 MOS/Diode/BJT는 각자의 실제 측정 항목을 사용한다.

회로의 Newton 수렴, 분기 전환, 강한 입력 변화, 새 Geometry와 공용 서버 부하는 단순 작업량으로 정확히 알 수 없다. 최초 준비가 필요하거나 기준과 다른 조건이면 불확실성이 더 크다.

## 예측에 사용하지 않은 회로 확인

기준은 1 fF / 40 µs CSVM이다. 아래 20 µs 결과는 기준 표 선택에서 제외했다. 수정된 캐시 측정 절차로 각 2회 실행했다.

| 변경 | 모델 | 예측 | 실측 | 상대 오차 |
|---|---|---:|---:|---:|
| T만 절반, dt_max 고정 | detailed | 0.1404 s | 0.1388 s | +1.2% |
| T만 절반, dt_max 고정 | simple | 0.0596 s | 0.0579 s | +2.9% |
| UI처럼 T와 dt_max 모두 절반 | detailed | 0.2005 s | 0.1567 s | +28.0% |
| UI처럼 T와 dt_max 모두 절반 | simple | 0.0851 s | 0.0621 s | +37.1% |

이 작은 확인에서도 UI 방식으로 시간을 바꾸면 28–37% 정도의 오차가 남았다. 네 조건 모두 0.5–2배 범위 안에 들었지만, 임의의 회로에 대한 정확도 보증으로 일반화하지 않는다.

## 재현

프로젝트 루트에서 다음 명령을 실행한다.

```bash
python scripts/benchmark_performance.py --repeats 5
```

출력은 server/data/performance_catalog.json과 docs/benchmarks/performance/에 저장된다. --cases로 comparison_id를 지정하면 일부만 다시 측정할 수 있다. 일부 실행은 지정 catalog 파일에 그 부분만 기록하므로 전체 기준표를 보존하려면 별도 --catalog 경로를 사용한다.

performance_cases.py는 순수 Python 입력/작업량 정의이며 수치 모델을 변경하지 않는다. 원시 실행시간, 입력, 실행 환경, solver 단계 수, 엔진 종류, 입력 해시는 기계 판독 가능한 JSON에 함께 저장했다. profile-cache를 잘못 비워 첫 반복에 준비 비용이 섞였던 이전 기록은 superseded-profile-cache/에 보관했으며 최종 표와 예측에서 제외했다.
